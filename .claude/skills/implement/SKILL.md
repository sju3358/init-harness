# 구현

구현은 Claude가 한다. 테스트 코드 작성과 검증은 Codex가 한다(Claude의 `src/test` 편집은 훅이 차단).

## 1. 전제

- 작업 worktree(`feat|fix/ITD-####`)의 세션이어야 한다. 원본 폴더(통합 브랜치)면 멈추고 해당 worktree 폴더에서 세션을 열도록 안내한다.
- `HANDOFF.md`의 "진행 위치"와 `git status`를 먼저 읽는다. 이어 하기면 거기서부터 계속한다.
- `PLAN.md` 상태가 `승인됨`이어야 한다. 아니면 `feature-plan`으로 돌아간다. 소스 편집이 `계획 승인 기록 없음`으로 차단되면 우회하지 않고 사용자에게 `계획 승인` 입력을 요청한다.
- `docs/prd/01-skillset.md`(규약), `docs/prd/02-common.md`(공통), `docs/project.md`(명령), `docs/api/`(이 feature의 엔드포인트)를 읽는다.
- 컨트롤러·DTO·에러 코드는 API 문서의 경로, 필드 이름, 타입, 필수, 검증 제약을 그대로 따른다. 문서와 다르게 만들어야 할 이유가 생기면 구현하지 않고 `prd-change`로 처리한다.

## 2. 구현

- `PLAN.md` 변경 파일 표 순서대로 구현한다. 파일은 에디터 도구(Edit·Write)로만 쓴다(셸 리다이렉션 금지).
- 파일 묶음(계획 표의 한 단위, 또는 파일 3~5개)을 마칠 때마다 `HANDOFF.md` "진행 위치"를 갱신한다: 끝난 파일, 진행 중인 파일과 남은 일, 다음 할 일, 그 사이에 내린 결정. 세션이 끊겨도(사용량 한도, 계정 전환) 새 세션이 이 내용과 `git diff`만으로 이어 갈 수 있어야 한다.
- 계획에 없는 파일·라이브러리·스키마 변경, 범위 변경이 필요해지면 멈춘다. 근거를 보여주고 사용자에게 `승인 취소`를 입력받은 뒤 `PLAN.md`를 고치고("계획 변경 이력"), `계획 승인`을 다시 받는다.
- 사소한 이탈(같은 파일 안 private 메서드 추가, 이름 조정)은 `PLAN.md` "계획 변경 이력"에 `기록만`으로 적고 진행한다.
- PRD가 침묵하거나 모순되면 추측으로 구현하지 않는다. 멈추고 `prd-change`로 처리한다.
- 테스트 코드는 쓰지 않는다. 시그니처 변경 등으로 기존 테스트를 고쳐야 하면 `HANDOFF.md` 다음 행동에 대상 테스트와 이유를 적어 Codex `test-write`로 넘긴다.

## 3. 구현 수정 요청 반영

- Codex 검증·테스트에서 나온 `HANDOFF.md` "구현 수정 요청" 중 처리가 `대기`인 항목을 모은다. 요청마다 근거(`파일:줄`, 실패 메시지)를 직접 확인한다.
- 코드 결함이면 고치고 처리 칸을 `반영`으로 바꾼다. 요청이 틀렸거나 PRD·계획 문제면 근거를 적어 `반려(사유)`로 두거나 `prd-change`·`feature-plan`으로 처리한다.

## 4. 마무리

- `docs/project.md`의 빌드 명령으로 컴파일 통과를 확인한다. 실패하면 원인을 고친다. 같은 방법으로 두 번 실패하면 보고한다. 테스트 실패는 Codex 단계에서 다룬다.
- `HANDOFF.md`에 변경 파일, 실행한 명령과 결과를 적고 다음 행동을 `Codex doc-code-verify`(수정 반영이면 요청한 검증 단계)로 갱신한다.
- 구현 결과를 "검증 완료", "PRD와 일치"로 보고하지 않는다. 검증은 Codex가 한다.
- 사용자에게 같은 worktree에서 Codex 세션을 열어 "HANDOFF 읽고 이어서 진행해"라고 하도록 안내한다. 테스트·검증 전에 커밋하려면 `itd-commit`을 쓴다(미검증 경고 후 사용자 판단).
