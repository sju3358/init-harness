# API 문서 설계·수정

API 문서는 PRD와 함께 승인 대상이다. 승인된 뒤 고치는 경우는 `prd-change` 흐름으로 진행하고, 그 안에서 이 스킬의 3·4단계를 따른다.

## 0. 준비

- `docs/prd/00-overview.md`, `docs/prd/02-common.md`, `docs/prd/features/F-##.md`, 기존 `docs/api/**`를 읽는다.
- 기존 프로젝트면 현재 컨트롤러 코드를 읽고 `node scripts/check-api.mjs` 출력으로 문서와 코드의 차이를 먼저 파악한다. 기존 API의 동작을 문서화할 때는 코드를 근거로 쓰고, 바꾸는 것은 PRD 근거가 있을 때만 바꾼다.
- 작업 브랜치가 `docs/ITD-####`인지 확인한다.

## 1. 공통 규약 (`README.md`)

- `02-common.md`의 API 규약(응답 포맷, 에러 코드, 인증, 페이지네이션, 형식)을 프론트가 바로 쓸 수 있는 형태로 옮긴다. 같은 내용을 두 곳에 따로 쓰지 않도록 `02-common.md`에는 설계 근거를, `README.md`에는 사용법(예시 JSON, 프론트 처리)을 쓴다.
- 비어 있는 규약(날짜 형식, null 처리 등)이 있으면 사용자에게 묻는다. 정해지지 않은 채로 엔드포인트를 쓰지 않는다.

## 2. 엔드포인트 설계

- feature 명세의 API 표에 있는 엔드포인트마다 `_template.md` 형식으로 쓴다. 파일은 도메인 단위로 나눈다(`orders.md`, `users.md`).
- 제목 줄은 `### API-### 메서드 경로` 형식을 지킨다. ID는 한번 정하면 바꾸거나 재사용하지 않는다.
- 각 엔드포인트에 `- 요구사항:`, `- feature:`, `- API 상태:`를 단다.
- 필드마다 타입, 필수, null 가능, 제약을 빠짐없이 쓴다. 프론트가 "이 필드가 없을 수도 있나?"를 물을 필요가 없어야 한다.
- 정상 응답 예시 JSON과, 해당 API에서 날 수 있는 에러(공통 에러 + 고유 에러)를 쓴다.
- PRD에 없는 필드·엔드포인트를 임의로 추가하지 않는다. 필요하면 사용자에게 제안하고, 받아들여지면 PRD(feature 명세)에도 반영한다.
- feature 명세의 API 표에는 ID·메서드·경로·요구사항만 두고 상세는 `docs/api/`를 가리킨다(두 곳에 상세를 쓰지 않음).
- `README.md` 엔드포인트 목록을 갱신한다.

## 3. 수정일 때

- 바꾸는 엔드포인트의 `API 상태`를 `변경`으로, 없애는 것은 `폐기 예정` 또는 `폐기`로 바꾼다. 문서에서 지우지 않는다.
- `CHANGELOG.md`에 버전, API ID, 바꾸기 전·후, 프론트 영향(`없음`·`추가 대응`·`수정 필요`), 근거를 적는다.
- `docs/api/README.md` 버전을 올린다.

## 4. 마무리

- `sh scripts/check-trace.sh prd`로 API ID·REQ·feature 연결 누락을 고친다.
- 기존 프로젝트면 `node scripts/check-api.mjs`를 다시 실행해 결과를 보고한다(새로 설계한 API는 아직 코드가 없으므로 `미구현`으로 나오는 게 정상).
- 프론트 전달용 요약을 만든다: 이번 버전의 API 수, 신규·변경·폐기 목록, `수정 필요` 항목. 사용자가 그대로 붙여 보낼 수 있는 짧은 텍스트로 준다.
- 다음 단계: `prd-verify` (API 문서도 함께 검증·승인).
