# 요구사항 도출

## 0. 준비

- `docs/project.md`를 읽는다. 비어 있으면 `project-init`부터 하라고 안내한다.
- 작업 브랜치가 `docs/ITD-####`가 아니면 티켓 번호를 묻고 통합 브랜치에서 `git switch -c docs/ITD-####`로 만든다.
- 기존 `docs/requirements.md`가 있으면 이어 쓰기다. 기존 ID를 바꾸거나 재사용하지 않는다.

## 1. 원문 수집

- Notion: 사용자가 준 페이지를 `notion-fetch`로 읽는다. 하위 페이지·링크된 DB도 범위에 들어가는지 묻고 읽는다. 분량이 커서 메인 컨텍스트를 많이 쓰면 Sonnet 서브에이전트에게 "원문 발췌 + 블록 위치"만 받아 온다(요약·해석 금지 지시).
- 대화: 사용자가 말한 요구는 그 자리에서 "대화 YYYY-MM-DD"로 출처를 남긴다.
- 원문을 읽지 않은 문서는 출처로 쓰지 않는다. 읽지 못한 링크는 보고한다.

## 2. 요구사항 작성

- 하나의 행은 하나의 판정 가능한 요구다. "관리 기능 제공"처럼 넓으면 쪼갠다.
- 인수 기준은 "입력·조건 → 기대 결과"로 쓴다. 원문에 기준이 없으면 지어내지 않고 미결 질문(Q-###)으로 보낸다.
- 원문끼리 다르면(Notion vs 대화, 페이지 vs 페이지) 양쪽 원문을 미결 질문에 그대로 적는다.
- 비기능(성능, 보안, 로그 보존 등)과 제약(기존 시스템, 고객사 환경)도 따로 뽑는다.
- 원문에 없지만 필요해 보이는 것은 요구사항에 넣지 않고 "제안"으로 미결 질문에 올린다.

## 3. 사용자 확인

- 미결 질문은 근거 원문을 같이 보여주며 묻는다. 답변란은 사용자 답으로만 채운다.
- 답을 받으면 해당 REQ의 상태를 `확정`으로 바꾸고 답변 출처를 적는다.
- 버전을 올리고(`v0.1` → `v0.2`) 개요의 출처 목록을 갱신한다.

## 4. 보고

- 요구사항 수(구분별), 미결 질문 수, 읽지 못한 원문을 보고한다.
- 다음 단계: `prd-write`. 미결 질문이 남아 있어도 진행할 수 있지만 그 REQ는 PRD에서 `미결`로 표시된다고 알린다.
