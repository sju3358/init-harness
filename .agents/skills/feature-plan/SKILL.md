# 개발계획

## 1. 작성

- 현재 브랜치가 `feat/ITD-####` 또는 `fix/ITD-####`이고 `artifacts/work/F-##/`가 있는지 확인한다. 없으면 `feature-start`부터.
- `sh .harness/hooks/prd-check.sh`를 다시 확인한다.
- `planner` 에이전트를 실행한다. 프롬프트에 대상 feature ID, PRD 버전, 재계획이면 바뀐 이유(PRD 변경, 계획 이탈 등)를 준다.

## 2. 확인

planner 결과를 그대로 넘기지 않고 메인 세션이 직접 확인한다.

- `sh scripts/check-trace.sh feature F-##`를 실행한다. 이 시점에는 테스트 관련 항목(`테스트 미연결`, `TC 미구현`)만 실패해야 정상이다. `계획 미반영`·`범위 밖`·`TC 없음`이 있으면 planner에게 다시 맡긴다.
- 인수 조건마다 TC가 있는지, TC의 기대 결과가 구체 값인지 본다.
- 변경 파일 표의 "재사용" 근거 `파일:줄`이 실제로 존재하는지 1~2개 열어 본다.

## 3. 확인 필요 항목

- `사람 승인 필요` 항목마다 근거(요구사항·PRD·현재 코드가 각각 무엇을 말하는지)와 추천안을 먼저 보여주고 답을 받는다. 답변란은 사용자 답으로만 채운다.
- PRD 자체의 문제는 `HANDOFF.md` "PRD 변경 요청"에 있는지 확인하고, 있으면 계획 승인으로 넘어가지 않고 멈춘다(Claude `prd-change` 필요).

## 4. 계획 승인

- 승인 요청 전에 요약한다: REQ 수, 변경 파일 수(신규/수정), TC 수, 신규 라이브러리·스키마 변경 여부, 남은 위험.
- `PLAN.md` 상태가 `승인 대기`인지 확인하고, 사용자에게 `계획 승인`을 한 줄로 입력하도록 안내한다. 다른 표현은 승인으로 보지 않는다.
- 승인 기록 메시지를 확인한 뒤 `PLAN.md` 상태를 `승인됨`으로 바꾸고 `HANDOFF.md` 다음 행동을 `implement`로 갱신한다.
