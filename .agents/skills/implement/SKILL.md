# 구현

## 1. 전제

- 작업 worktree(`feat|fix/ITD-####`)에서 연 세션이어야 한다. 원본 폴더(통합 브랜치)면 멈추고 해당 worktree 폴더에서 세션을 열도록 안내한다.
- `PLAN.md` 상태가 `승인됨`이어야 한다. 아니면 멈추고 Claude `feature-plan`이 필요하다고 안내한다. 소스 편집이 `계획 승인 기록 없음`으로 차단되면 우회하지 않고 사용자에게 `계획 승인` 입력을 요청한다.
- `docs/prd/01-skillset.md`(규약), `docs/prd/02-common.md`(공통), `docs/project.md`(명령), `docs/api/`(이 feature의 엔드포인트)를 읽는다.
- 컨트롤러·DTO·에러 코드는 API 문서의 경로, 필드 이름, 타입, 필수, 검증 제약을 그대로 따른다. 문서와 다르게 만들어야 할 이유가 생기면 구현하지 않고 "PRD 변경 요청"으로 올린다.

## 2. 구현

- `PLAN.md` 변경 파일 표 순서대로 구현한다. 파일은 apply_patch로만 쓴다(셸 리다이렉션 금지).
- `PLAN.md`는 고치지 않는다(훅이 차단). 계획에 없는 파일·라이브러리·스키마 변경, 기존 테스트 수정, 범위 변경이 필요해지면 즉시 멈춘다. `HANDOFF.md` "계획 변경 요청"에 유형 `재승인 필요`로 적고, 사용자에게 같은 worktree의 Claude 세션에서 `feature-plan`(재계획)을 하도록 안내한다.
- 사소한 이탈(같은 파일 안 private 메서드 추가, 이름 조정)은 "계획 변경 요청"에 유형 `기록만`으로 적고 진행한다.
- PRD가 침묵하거나 모순되면 추측으로 구현하지 않는다. `HANDOFF.md` "PRD 변경 요청"에 적고 멈춘다.
- 테스트 코드는 이 단계에서 쓰지 않는다(`test-write`). 단, 빌드를 위해 기존 테스트를 고쳐야 하면 계획 이탈로 적는다.

## 3. 마무리

- `docs/project.md`의 빌드 명령을 실행해 통과를 확인한다. 실패하면 원인을 고친다. 같은 방법으로 두 번 실패하면 보고한다.
- `HANDOFF.md`에 변경 파일, 실행한 명령과 결과, 다음 행동(`doc-code-verify`)을 적는다.
- 구현 결과를 "검증 완료", "PRD와 일치"로 보고하지 않는다. 검증은 다음 단계에서 `verifier`가 한다.
