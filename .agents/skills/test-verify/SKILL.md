# 테스트 검증

구현 코드는 고치지 않는다(셸 쓰기 포함). 실패는 원인을 분류해 기록하고, 구현 결함이면 버그 리포트를 쓰고 멈춘다. 수정은 Claude `implement`가 한다.

## 1. 재실행 범위

`artifacts/work/F-##/test-status.md`로 이번 회차에 돌릴 TC를 정한다. 파일이 없으면 `_template/`에서 복사해 모든 TC를 `미실행`으로 둔다.

- 돌린다: 상태가 `FAIL`·`미실행`인 TC. 명세 누락으로 테스트가 없는 TC는 제외하고 범위 칸에 사유를 적는다(해소 전까지 완료 불가)
- 건너뛴다: 상태가 `PASS`인 TC. 단, `git diff <그 TC의 마지막 실행 커밋>..HEAD --name-only`에 그 TC의 "관련 소스"나 테스트 파일이 있으면 그 TC만 골라 다시 돌린다.
- 중간 회차에서는 전체 테스트를 돌리지 않는다. 전체 회귀(`docs/project.md`의 단위·통합 테스트 명령 전체)는 6단계 완료 판정에서 반드시 한 번 하고, 그 밖에는 사용자가 요청할 때만 한다.
- 고른 TC 목록과 고른 이유(FAIL·미실행·영향)를 실행 전에 `TEST-REPORT.md` "실행"의 범위 칸에 적는다.

## 2. 실행

- 고른 TC만 실행하고, 첫 실패에서 멈추는 옵션을 쓴다. 예: Gradle `gradle test --fail-fast --tests 'demo.OrderTest.rejectsWhenOutOfStock'`, Maven `mvn test -Dtest='OrderTest#rejectsWhenOutOfStock' -Dsurefire.skipAfterFailureCount=1`. 명령 형태는 `docs/project.md`의 테스트 명령을 따른다.
- 결과(성공·실패·건너뜀 수, 첫 실패에서 중단됐는지)와 실패 메시지 원문을 `TEST-REPORT.md` "실행"에 적는다.
- 실행한 TC의 상태와 마지막 실행(일시·커밋)을 `test-status.md`에 갱신한다. 중단돼 실행되지 않은 TC는 이전 상태 그대로 둔다.

## 3. 실패 처리

첫 실패가 나오면 나머지 TC를 이어서 돌리지 않는다. 먼저 원인을 분류한다.

| 원인 | 판단 근거 | 처리 |
| --- | --- | --- |
| 테스트 코드 자체 오류 | 테스트 준비 데이터·호출 방법·문법이 틀림. 기대값은 문서와 맞음 | 테스트 코드만 고치고(`test-write` 기준) 그 TC만 다시 실행. 기대값을 구현에 맞춰 바꾸는 것은 이 경우가 아님 |
| 구현 결함 | 문서(PRD·PLAN·API) 기준 기대값과 실제 결과가 다름 | 버그 리포트를 쓰고 멈춤 |
| 명세 누락 | 문서가 그 동작을 정하지 않아 기대값 근거가 없음 | `TEST-REPORT.md` "명세 누락"과 `HANDOFF.md` "PRD 변경 요청"에 적고, 그 TC를 `미실행`(명세 누락)으로 돌려 제외한 뒤 나머지 TC로 계속. 해소 전까지 완료 불가 |
| 환경 | DB·컨테이너·네트워크·도구 미설치 | 오류 원문을 적고 사용자에게 보고하고 멈춤 |

- 테스트 오류인지 구현 결함인지 판단할 근거가 부족하면 구현 결함으로 보고 버그 리포트를 쓴다(추측으로 테스트를 고치지 않음).
- 버그 리포트는 `HANDOFF.md` "구현 수정 요청"에 쓴다: 실패한 시나리오(TC·테스트 `파일:메서드`), 관련 REQ·PRD(`문서#섹션`), 기대값(문서 원문), 실제값(실패 메시지·응답 원문), 재현 방법(실행 명령), 의심 지점(`파일:줄`). 의심 지점은 읽고 적기만 하고 코드는 고치지 않는다.
- 멈출 때 `HANDOFF.md` 상태를 `차단`, 다음 행동을 `Claude implement(구현 수정 요청 반영)`으로 적고, 사용자에게 같은 폴더의 Claude 세션에서 "구현 수정 요청 반영해"라고 하도록 안내한다.
- Claude가 `반영`한 뒤 다시 이 스킬을 실행하면 1단계 규칙대로 실패했던 TC, 미실행 TC, 수정 파일과 관련된 PASS TC만 돌린다.

## 4. 유효성 판정

- 고른 TC가 모두 `PASS`가 되면 `verifier` 에이전트를 `mode=test`로 실행해 "테스트 유효성"을 채우게 한다. 이미 `유효` 판정을 받았고 그 뒤 테스트 파일이 바뀌지 않은 TC는 다시 판정받지 않는다.
- `약함`·`무효` 판정은 `test-write`로 돌아가 고친 뒤 그 TC만 다시 실행·판정한다.
- 메인 세션은 `유효` 판정 중 1~2개를 골라, 테스트 대상 코드의 해당 조건이 깨지면 이 테스트가 실패할지를 코드를 읽고 판단한다. 소스를 실제로 바꿔 돌려보지 않는다.

## 5. 추적표

- `docs/traceability.md`의 이 feature REQ 행에 구현 위치, 테스트(`TC`), 결과를 채운다. 결과는 `test-status.md`의 실제 실행 상태로만 쓴다(실행 안 했으면 `미검증`).

## 6. 완료와 커밋 준비

완료 판정은 전체 회귀 통과가 필수다. 선별 실행만으로 완료로 판정하지 않는다.

- `test-status.md`의 모든 TC가 `PASS`이고 유효성 판정에 `약함`·`무효`가 없으면 전체 회귀를 실행한다(사용자에게 묻지 않음). 첫 실패 중단 옵션은 그대로 쓴다.
- 결과를 `TEST-REPORT.md` "실행"(범위 `전체 회귀`)과 `test-status.md` "마지막 전체 회귀"(일시·커밋·결과)에 기록한다.
- 실패가 나오면 3단계로 처리하고 멈춘다. 이 feature의 TC가 아닌 테스트가 실패해도 같다(회귀 결함). 수정이 반영되면 다시 선별 실행부터 하고, 모두 `PASS`가 되면 전체 회귀를 다시 한다.
- 완료 조건: 전체 회귀가 실패 0건이고, 그 실행 커밋 이후 소스·테스트 파일 변경이 없음(`git diff <전체 회귀 커밋>..HEAD --name-only`와 작업 트리 변경으로 확인). 하나라도 어긋나면 `HANDOFF.md` 상태를 `완료`로 쓰지 않는다.
- 요약 보고: 이번 회차 범위와 결과 수, `test-status.md` 상태별 TC 수, TC별 유효성, 전체 회귀 결과, `확인 못한 부분`, 남은 `PRD 변경 요청`.
- 완료 조건을 충족하고 남은 문제가 없으면 `HANDOFF.md` 상태를 갱신하고 다음 행동을 `Claude itd-commit`으로 적은 뒤 멈춘다. 커밋·push는 Codex가 하지 않는다. 사용자에게 같은 폴더의 Claude 세션에서 "커밋해줘"라고 하도록 안내한다.

## Claude 대행

Codex를 쓸 수 없어 사용자가 Claude에게 대행을 요청한 경우(`docs/rules/workflow.md` "대행 작업").

- `verifier` 대신 `code-verifier` 에이전트를 `mode=test`로 실행한다. 메인 세션 재검증은 그대로 한다.
- 빌드·테스트·검사 스크립트는 실행해도 된다. 검증 중에는 소스·`PLAN.md`를 고치지 않고, 테스트는 고칠 수 없다(훅이 차단).
- `수정 필요`가 나와도 테스트는 고치지 않는다. `TEST-REPORT.md`에 판정을 남기고, 소스 결함은 "구현 수정 요청"(Claude `implement`로 처리), 테스트 결함은 "대행 기록"의 "원래 담당이 할 일"에 적은 뒤 멈춘다.
