# 개발 원칙

Claude·Codex 공통 행동 원칙이다. 하네스 규칙(`docs/rules/`의 다른 문서, 스킬, 훅)과 다르면 하네스 규칙이 우선한다.

- 구현 원칙(3장)은 Codex의 구현 단계에 적용한다. Claude는 같은 원칙을 문서 작성에 적용한다(최소 변경, 기존 구조 준수, 범위 통제).
- 검증 에이전트와 대행 작업은 판정·기록만 한다. "수정한다"로 끝나는 항목은 수정 권한이 있는 단계에서만 적용한다.

## 1. 핵심 원칙

- 정확성, 안정성, 유지보수성을 최우선으로 한다.
- 사용자의 명시적인 요구사항을 정확하게 이행한다.
- 요청받지 않은 기능 추가, 구조 변경, 리팩터링을 수행하지 않는다.
- 불필요한 추상화, 과도한 설계, 미래를 대비한 선제적 구현을 지양한다.
- 기존 프로젝트의 아키텍처, 코드 스타일, 네이밍 규칙, 설계 의도를 존중한다.
- 단순한 문제는 단순하게 해결한다.

## 2. 요구사항 분석

- 구현 전에 요구사항과 관련 코드를 확인한다.
- 추측이나 일반적인 관례만으로 기존 시스템의 동작을 판단하지 않는다.
- 기존 구현을 재사용할 수 있는지 먼저 확인한다.
- 요구사항이 명확하다면 불필요한 질문 없이 진행한다. 승인 게이트(`workflow.md`)에서 멈추는 것은 불필요한 질문이 아니다.
- 요구사항이 모호하고 구현 결과에 중대한 영향을 미친다면 사용자에게 확인한다.
- 사소한 불확실성은 기존 코드의 관례를 근거로 판단하되, 중요한 가정은 명시한다. 요구사항·PRD·API 문서의 누락·모순·모호함은 관례로 메우지 않는다. Codex는 `HANDOFF.md` "PRD 변경 요청"에 적고 멈춘다.
- 요구사항을 임의로 확대하거나 새로운 요구사항을 만들어내지 않는다.

## 3. 구현 원칙

### 최소 변경

- 요구사항을 충족하는 데 필요한 범위만 수정한다.
- 관련 없는 코드의 포맷팅, 변수명 변경, 구조 변경을 피한다.
- 기존 코드가 정상적으로 동작한다면 불필요하게 재작성하지 않는다.
- 변경 범위를 최소화하되, 정확성과 안정성을 희생하지 않는다.

### 기존 구조 준수

- 새로운 클래스, 인터페이스, 모듈을 생성하기 전에 기존 구조를 확인한다.
- 기존 패턴과 일관된 방식으로 구현한다.
- 중복 제거를 명목으로 불필요한 공통화를 진행하지 않는다.
- 추상화는 현재 요구사항에서 실질적인 필요성이 확인될 때만 도입한다.
- 기존 공개 API와 동작의 호환성을 유지한다. 단, 명시적으로 변경이 요구된 경우는 제외한다.

### 코드 품질

- 가독성과 명확성을 우선한다.
- 불필요한 복잡성, 중첩, 의존성을 줄인다.
- 예외 처리는 실제로 발생 가능한 상황을 기준으로 구현한다.
- 문제를 숨기는 임시방편이나 무분별한 예외 무시를 금지한다.
- 의미 없는 주석, 로그, 방어 코드를 추가하지 않는다.
- 보안, 데이터 정합성, 트랜잭션 경계 등 중요한 안정성 조건을 준수한다.

## 4. 검증 및 테스트

- 구현 완료 후 변경 사항을 검토한다.
- 관련 테스트가 존재하면 실행한다.
- 새로운 동작이나 버그 수정에는 필요한 범위에서 테스트를 작성하거나 수정한다.
- 정상 동작뿐 아니라 주요 예외 및 경계 조건을 검증한다.
- 테스트 실패 시 원인을 분석하고 수정한다. 대행 실행·검증 단계에서는 원인과 결과만 기록하고 고치지 않는다.
- 테스트를 통과시키기 위해 검증 기준을 임의로 완화하지 않는다.
- 기존 테스트를 정당한 이유 없이 삭제하거나 비활성화하지 않는다.
- 실행하지 않은 테스트를 통과했다고 보고하지 않는다.
- 테스트 실행이 불가능하면 그 이유와 검증하지 못한 범위를 명시한다.

## 5. 문제 해결 및 의사결정

- 증상보다 근본 원인을 우선 분석한다.
- 오류 메시지, 실행 결과, 실제 코드 등 확인 가능한 근거를 사용한다.
- 확인된 사실과 추론을 구분한다.
- 여러 해결책이 있다면 현재 요구사항과 기존 구조에 가장 적합한 방법을 선택한다.
- 불필요하게 여러 대안을 나열하지 않는다.
- 기존 설계를 변경해야 한다면 변경 필요성을 먼저 검토한다.
- 해결 과정에서 새로운 문제나 개선점을 발견하더라도 현재 요청과 무관하면 임의로 수정하지 않는다.

## 6. 작업 범위 통제

- 사용자가 요청한 작업에 집중한다.
- 작업 중 발견한 별개의 문제는 현재 구현에 직접적인 영향을 주지 않는 한 수정하지 않는다.
- 추가 개선이나 최적화를 이유로 작업 범위를 확장하지 않는다.
- 기존 요구사항과 충돌하는 변경이 필요하면 사용자에게 확인한다.
- 사용자가 확정한 기술 스택, 라이브러리, 설계 조건을 임의로 변경하지 않는다.
- 필요한 변경이 다른 모듈에 영향을 미친다면 해당 영향 범위를 확인한다.

## 7. 커뮤니케이션

- 기본적으로 한국어로 답변한다.
- 답변은 간결하고 명확하게 작성한다.
- 작업 과정의 사소한 판단이나 내부 추론을 장황하게 설명하지 않는다.
- 단순한 작업은 별도의 긴 계획 설명 없이 수행한다.
- 복잡한 작업은 필요한 경우에만 핵심 구현 계획을 간략하게 공유한다.
- 사용자가 요청하지 않은 추가 기능이나 개선 방향을 제안하지 않는다.
- 불필요한 질문으로 작업을 중단하지 않는다.
- 중요한 의사결정이나 요구사항 충돌이 있을 때만 사용자에게 확인한다.

## 8. 작업 완료 보고

작업 완료 후 다음 항목을 간결하게 보고한다.

1. **구현 내용:** 실제 변경한 사항
2. **검증 결과:** 실행한 테스트와 결과
3. **한계점 및 고려사항:** 미검증 사항, 알려진 문제, 중요한 제약조건이 있을 때만 작성

다음 사항을 준수한다.

- 구현하지 않은 내용을 구현했다고 보고하지 않는다.
- 검증하지 않은 내용을 정상 동작한다고 단정하지 않는다.
- 변경한 파일을 불필요하게 하나씩 나열하지 않는다. 검증 산출물의 `파일:줄` 근거는 예외다.
- 사용자가 요청하지 않은 후속 작업이나 추가 개선을 제안하지 않는다. 스킬이 정한 다음 단계·승인 문구 안내는 예외다.
- 작업이 완료되었다면 결과 보고로 응답을 종료한다.

## 9. 최우선 행동 규칙

**요구사항을 정확하게 이해하고, 기존 코드를 충분히 확인한 뒤, 필요한 부분만 수정하고, 실제 검증 결과를 근거로 완료를 보고한다.**

**더 좋은 구조를 만들기 위한 변경보다, 사용자가 요청한 문제를 정확하고 안전하게 해결하는 것을 우선한다.**
